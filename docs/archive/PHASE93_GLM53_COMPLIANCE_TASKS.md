## §1 为什么只做"用户数据导出/删除"这一块

🔒-4 里四项，**只有这一项能在离线环境真做完**：

| 项 | 能否在本环境做 |
|---|---|
| 等保测评 | ❌ 需外部测评机构 |
| 数据出境 | ❌ 涉及跨境链路与法务 |
| 隐私合规体系 | ❌ 需制度与流程 |
| **用户数据导出 / 删除** | ✅ **纯代码 + 数据库，可端到端验证** |

> 判据（本项目已多次生效）：**优先选"在本环境能验完"的项**。
> 依赖外部机构/基建的项，离线环境里必然变成纸上完成。

而且它是**强合规要求**（个人信息保护法明确：个人有权查阅、复制、删除其个人信息），
不做等于对外商业化时存在明确的法律缺口。

## §3 任务

### T1（P0）枚举用户数据清单

- grep 全仓含 `userId` / `user_id` / `createdBy` / `ownerId` 的实体，产出完整表
- 每个实体标注：**是否属于"个人信息"**、删除时如何处理（硬删 / 匿名化 / 保留）
- **审计日志必须保留**（合规要求：操作留痕不能因用户删除而消失），但其中的用户名建议匿名化

### T2（P0）用户数据导出

- 接口：`GET /api/admin/users/{userId}/data-export`（管理员）与本人自助入口
- 输出：**结构化 JSON**（机器可读、可携带），覆盖 T1 全部实体
- 字段：导出时间、租户、用户基本信息 + 各模块数据
- **不做**：不导出他人数据；不导出密码哈希 / token 等凭据字段

### T3（P0）用户数据删除 / 匿名化

- 接口：`DELETE /api/admin/users/{userId}/data-erasure`
- 策略：
  - 业务数据（IM 消息、回应、已读、会话、AI 对话、成员关系）→ **匿名化或软删**
  - 审计日志 → **保留**（仅将用户名替换为匿名标识）
  - 账号本身 → 置为已注销 / 匿名
- 必须**租户隔离**：只能处理本租户用户
- **严禁硬删审计日志**（会破坏 PHASE83–85 建起来的留痕能力）

### T4（P0）权限与留痕

- 权限：仅 ADMIN 或本人
- 跨租户访问 → **403**
- 导出/删除操作**本身必须记审计留痕**（复用 `AuditService.log`，
  action 建议 `user.data.export` / `user.data.erasure`）
  —— 这两条新增接口会触发覆盖度门禁（PHASE84 建），请确保它们有埋点

### T5（P0）端到端验证 —— 本批验收核心

**真实 HTTP，不用 mock**（脚本可参照 `scripts/quota-e2e-verify.py` 的风格）：

1. 导出：造一个有多模块数据的用户 → 导出 → 断言 JSON 含这些模块的数据
2. 删除：执行 erasure → 断言业务数据已匿名化、**审计日志仍在**
3. 跨租户：用 A 租户管理员操作 B 租户用户 → 断言 **403**
4. 留痕：断言 `user.data.export` / `user.data.erasure` 审计记录真的产生

> 每个"被拒"断言最好配一条**反证**（如：同租户操作应成功），
> 否则无法区分 403 来自租户隔离还是鉴权/参数问题。

## §5 红线（违反即打回）

1. **严禁导出漏表** —— T1 的清单要完整，导出须覆盖全部含用户数据的实体
2. **严禁硬删审计日志** —— 只做匿名化，留痕能力不得被破坏
3. **严禁导出/删除他人数据** —— 必须租户隔离 + 权限校验
4. **严禁导出凭据字段**（密码哈希、token、refresh token、密钥）
5. **严禁只做单测** —— 必须有真实 HTTP 的端到端验证（T5）
6. **严禁编造验证结果或虚报门禁数字**
   （本项目 PHASE83 曾出现"前端零改动却报 vitest +10"，一看改动范围就穿帮）
7. 严禁修改已应用的迁移文件
